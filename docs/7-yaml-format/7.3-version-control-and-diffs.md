# Version control and diffs

A Catenator spec is a versioned artifact. Every change to the spec produces a new version. This section defines how versions are assigned, how changes are tracked, and what a diff between two spec versions means.

---

## Spec versioning

The spec `version` field follows semver — `MAJOR.MINOR.PATCH`.

| Increment | When to use |
|---|---|
| `PATCH` | Clarifications, wording corrections, `source` field updates — no structural change |
| `MINOR` | Adding macros, mesos, or micros; adding attachments; updating `display-name` — additive changes |
| `MAJOR` | Removing macros, mesos, or micros; changing `name` identifiers; changing `descriptor` types; changing pinned versions — breaking changes |

A version bump is the only required change when updating a spec. The `authored` field MUST be updated to the date of the new version. All other fields carry forward unless changed.

---

## What constitutes a change

A change is any modification to the spec YAML that alters its content. This includes:

- Adding, removing, or renaming any `name` field at any level
- Changing any `display-name` or `display-name-source`
- Adding, removing, or modifying any `definition`
- Adding, removing, or changing any `vocabulary` address
- Adding or removing attachments
- Changing any pinned version field
- Changing `spec.status`

Reformatting the YAML — whitespace, comment changes, key reordering — is not a change if the parsed content is identical.

---

## Version registry

All published spec versions and their changes are recorded in `VERSIONS.md` in the `catenator-standard` repository. This is the authoritative change record for the standard and for all specs that reference it.

Each entry in the registry records:

```markdown
## [1.1.0] — 2026-03-21

### Added
- `display-name` and `display-name-source` required on all items
- `specimen` field added to system declaration
- `injected` field added to macros

### Changed
- `spec.authored` type changed to ISO date string

### Removed
- nothing
```

The registry uses the Keep a Changelog format. Entries are written by the spec author or the Catenator tooling, not generated automatically.

## Diffs

A diff between two spec versions is a structured comparison of their YAML content at each level — system, macro, meso, micro.

### What a diff surfaces

| Change type | Diff signal |
|---|---|
| Macro added | `+ macro: name` |
| Macro removed | `- macro: name` |
| Meso added | `+ meso: macro.name` |
| Meso removed | `- meso: macro.name` |
| Micro added | `+ micro: name (in meso)` |
| Micro removed | `- micro: name (in meso)` |
| `display-name` changed | `~ display-name: old → new` |
| `display-name-source` changed | `~ display-name-source: authored → inferred` |
| `definition` changed | `~ definition: changed` |
| `descriptor` changed | `~ descriptor: model → rule` |
| `vocabulary` changed | `~ vocabulary: old-address → new-address` |
| `injected` changed | `~ injected: false → true` |
| Version field changed | `~ standard-version: 1.0.0 → 1.1.0` |

### What a diff does not surface

- Changes to `source` fields — these are authoring notes, not part of the spec contract
- Whitespace and formatting changes
- Comment changes

### Breaking vs non-breaking diffs

A diff is **breaking** if it contains any of:
- A removed macro, meso, or micro
- A changed `name` identifier at any level
- A changed `descriptor` type
- A downgraded `standard-version`, `vocabulary-version`, or `library-version`

A breaking diff MUST increment `MAJOR`. Any agent or tool that consumed the previous version MUST be re-validated against the new version before use.

A diff is **non-breaking** if it contains only additions or clarifications. Non-breaking diffs increment `MINOR` or `PATCH`.

---

## Bundle versioning

The spec bundle (`manifest.yaml`) records the spec version alongside the sha256 of each attachment. When the spec version changes, the manifest MUST be updated. When an attachment changes, its sha256 in the manifest MUST be updated — this constitutes a `MINOR` increment in the spec version even if the YAML spec itself is unchanged, because the bundle's content has changed.

A bundle is uniquely identified by its `spec.version`. Two bundles with the same `spec.version` MUST have identical content — same YAML, same attachments, same sha256 values. A bundle with a changed attachment but the same `spec.version` is invalid.

---

## Upgrading a spec

Upgrading a spec from one pinned version to another — for example, when a new library version introduces a new meso — is a deliberate authoring operation:

1. The tooling diffs the current spec against the new library or vocabulary version
2. Changes are surfaced to the author — new mesos available, deprecated terms, changed definitions
3. The author accepts or rejects each change
4. Accepted changes are applied and the spec is re-authored at the new version
5. The `spec.version` is incremented appropriately
6. The manifest is updated

Upgrading is never automatic. The spec is always re-authored by a human. The tooling surfaces the delta; the author decides.
