# Schema reference

A Catenator spec is a YAML document. This section defines every field in the format — its name, type, whether it is required, and what it governs.

All specs conforming to this standard MUST be valid YAML. Fields marked **required** MUST be present. Fields marked **optional** MAY be omitted. A spec missing a required field is invalid and MUST NOT be executed by any agent or tool.

---

## Spec header

The spec header is the first block in every spec file. It identifies the spec itself and pins the versions of the standard, vocabulary, and library it was authored against.

```yaml
spec:
  version: "1.0.0"
  authored: "2026-03-21"
  status: ground-truth
  standard-version: "1.0.0"
  vocabulary-version: "3.0.0"
  library-version: "2.0.0"
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `version` | semver string | required | The version of this spec — incremented when the spec is updated |
| `authored` | ISO date string | required | The date this version of the spec was authored |
| `status` | enum | required | The current state — `draft`, `ground-truth`, `published`, `deprecated` |
| `standard-version` | semver string | required | The version of the Catenator standard this spec was authored against |
| `vocabulary-version` | semver string | required | The version of the vocabulary package referenced in this spec |
| `library-version` | semver string | required | The version of the spec library (macro and meso definitions) this spec was authored against |

**Version pinning:** All three version fields are immutable once set for a given spec version. An agent reading the spec MUST use the pinned versions — not the latest available. Upgrading a spec to a new library or vocabulary version is a deliberate authoring operation that produces a new spec version.

## System declaration

The system block declares what is being specified. There is exactly one system block per spec.

```yaml
system:
  name: restaurant-ordering-system
  display-name: "Table ordering"
  display-name-source: inferred
  specimen: restaurant
  attachments:
    - ref: inputs/brief.md
    - ref: inputs/mockup.fig
      notes: "checkout screen, page 4"
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `name` | string | required | The canonical machine-readable identifier for the system — kebab-case, unique within the bundle |
| `display-name` | string | required | The human-readable name of the system as it should appear in any output |
| `display-name-source` | enum | required | `authored` — the author specified this name; `inferred` — the agent may refine |
| `specimen` | string | optional | The specimen type this system is an instance of — governs default macro set and vocabulary |
| `attachments` | list | optional | Bundle-relative paths to attachments relevant to the system as a whole |

---

## Macros

A macro is a top-level bounded subsystem. A spec contains one or more macros.

```yaml
macros:
  - name: store
    display-name: "Order"
    display-name-source: inferred
    source: "customers browse the menu, place orders from their table"
    injected: false
    attachments:
      - ref: inputs/mockup.fig
        notes: "order flow, pages 2–5"
    mesos:
      - ...
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `name` | string | required | The canonical identifier for the macro — matches the spec library definition |
| `display-name` | string | required | The human-readable name — what the output calls this subsystem |
| `display-name-source` | enum | required | `authored` or `inferred` |
| `source` | string | optional | The prose fragment or reasoning that justifies the inclusion of this macro |
| `injected` | boolean | optional | `true` if the macro is a cross-cutting structural default, not derived from prose. Defaults to `false`. |
| `attachments` | list | optional | Bundle-relative paths to attachments governing this macro |
| `mesos` | list | required | One or more meso declarations within this macro |

---

## Mesos

A meso is a named pattern within a macro — composed of micros. A macro contains one or more mesos.

```yaml
  mesos:
    - name: store.cart
      display-name: "Your order"
      display-name-source: inferred
      source: "diners accumulate items before submitting to kitchen"
      attachments:
        - ref: inputs/mockup.fig
          notes: "cart panel, page 3"
      micros:
        - ...
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `name` | string | required | The canonical identifier — namespaced to its macro: `macro.meso` |
| `display-name` | string | required | The human-readable name |
| `display-name-source` | enum | required | `authored` or `inferred` |
| `source` | string | optional | The prose fragment justifying inclusion |
| `attachments` | list | optional | Bundle-relative paths to attachments governing this meso |
| `micros` | list | required | One or more micro declarations within this meso |

---

## Micros

A micro is an atomic spec item — not further decomposable. A meso contains one or more micros.

```yaml
      micros:
        - name: cart
          display-name: "Order"
          display-name-source: inferred
          descriptor: model
          definition: "The persistent collection of items a diner has selected"
          vocabulary: vocabulary.<package>.<module>.<term>
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `name` | string | required | The canonical identifier for the micro — unique within its meso |
| `display-name` | string | required | The human-readable name — what the output calls this item |
| `display-name-source` | enum | required | `authored` or `inferred` |
| `descriptor` | enum | required | The Catenator descriptor type — `model`, `operation`, `rule`, `event`, `process`, `actor`, `service`, `integration`, `utility`, `risk` |
| `definition` | string | required | A precise, single-sentence definition of what this micro is |
| `vocabulary` | string | optional | A vocabulary address linking this micro to a canonical vocabulary term |
| `source` | string | optional | The prose fragment justifying inclusion |

---

## Attachments

Attachments are files included in the bundle that extend the spec with authored intent. They appear at system, macro, or meso level.

```yaml
attachments:
  - ref: inputs/brief.md
    role: source
    notes: "the original prose brief"
  - ref: inputs/mockup.fig
    role: ux-intent
    notes: "checkout screen, page 4"
```

| Field | Type | Required | Definition |
|---|---|---|---|
| `ref` | string | required | The bundle-relative path to the attachment file |
| `role` | enum | optional | The function of the attachment — `source`, `ux-intent`, `visual-intent`, `brand`, `data` |
| `notes` | string | optional | Free-text annotation — page reference, scope note, or other context |

The `sha256` hash for each attachment lives in `manifest.yaml`, not in the spec. The spec references; the manifest pins.

---

## `display-name-source` values

| Value | Meaning |
|---|---|
| `authored` | The author specified this name. The output MUST use it exactly. The agent MUST NOT substitute its own judgment. |
| `inferred` | A suggested name is provided as a starting point. The agent may refine based on domain context. |

`display-name` is required at every level — macro, meso, and micro. A spec with any item missing `display-name` or `display-name-source` is invalid.

---

## Descriptor types

The `descriptor` field on a micro declares which Catenator descriptor the item belongs to.

| Value | What it specifies |
|---|---|
| `model` | A data structure the system operates on |
| `operation` | An individual action the system performs |
| `rule` | A constraint the system must enforce |
| `event` | Something the system must respond to |
| `process` | A workflow the system executes |
| `actor` | Who or what interacts with the system |
| `service` | A capability the system exposes or consumes |
| `integration` | A boundary with an external system |
| `utility` | What the system does, for whom, and to what end |
| `risk` | What can go wrong, how likely, and who bears it |

---

## Vocabulary references

A vocabulary address links a micro to a canonical term definition in the vocabulary package. The format is a dot-separated path:

```
vocabulary.<package>.<module>.<term>
```

Vocabulary addresses are resolved against the `vocabulary-version` pinned in the spec header. An agent MUST NOT resolve addresses against a different vocabulary version.

If a vocabulary term does not exist at the pinned version, the micro definition stands on its own — the `vocabulary` field is informational, not required for execution.
