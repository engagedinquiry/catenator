# Prose to spec — how a governing document becomes a Catenator spec
## Section 9.3 — Catenator standard documentation

This section traces how prose from a governing document becomes entries in a Catenator spec. The example system is a live consultancy website with a published governing document. Every spec entry shown here is traceable to a specific governing document decision.

Reading this section, you will understand:
- How to identify macros, mesos, and micros from prose
- How to choose the right descriptor for each item
- What to retain, what to abstract, and what to exclude
- The test for a technology-agnostic spec

---

## The governing document

The system described here was built from a governing document that preceded the build. The document specifies five dimensions of digital experience — Screen, Context, Content, Time, and Trust — and describes how each is expressed in the system. Every spec entry traces back to a named decision in that document.

The governing document is attached to the spec as a source attachment. It is the chain of provenance: author → governing document → spec → build.

---

## The first decision: identifying macros

**Governing document says:**
> *"Every digital product is defined by five dimensions. A screen is the surface. Context is who is reading. Content is what is said. Time is what the system remembers. Trust is what is visible to the reader about how the system works."*

**Spec produces:** Five macros — `screen`, `context`, `content`, `time`, `trust`.

**Translation note:**
The dimensions arrive pre-named in the governing document. This is unusually clean. In most systems, identifying macros requires judgment — the governing document rarely names the top-level subsystems explicitly. Here the author did the decomposition before the build. The spec trusts that taxonomy.

When a governing document does not name its macros, the agent must identify bounded subsystems by asking: what are the distinct, separable concerns of this system? Each concern that has its own actors, rules, and behaviours is a candidate macro.

---

## Screen macro — colour as a governed decision

**Governing document says:**
> *"The background colour signals where you are and what context the site is reading you as. Dark on the home page — no signal yet. [path colour] on the Design path. [path colour] on the Technical path."*

**Spec produces:** `screen.context-colours` meso. One `model` micro per route. One `rule` micro for the transition.

**Translation decisions:**

The exact colour values are authored decisions — the spec carries them. A spec that omitted the values and said "appropriate colours per context" would force the agent to choose. The author chose. The spec records the choice.

The transition duration is also an authored decision. It appears in the spec as a rule: the background transitions over a specified duration on route change. The exact value is in the spec. An agent building from this spec must implement that duration — not substitute their own judgment.

**What is excluded:**
The CSS mechanism — which property carries the colour, whether it is applied as a class or an inline style — is excluded. The spec says the background transitions. It does not say how the transition is implemented. One build might use a CSS class. Another might use an inline style. Both satisfy the spec.

---

## Context macro — persona as an emergent property

**Governing document says:**
> *"The bar does not ask you what you are. It reads what you have done. The persona is not declared — it is earned through reading."*
> *"Persona is [state name] when Design and Technical engagement is roughly equal."*

**Spec produces:** `persona-states` model, `shopper-threshold` rule, `persona-update` rule.

**Translation decisions:**

"Roughly equal" is not precise enough for a spec. The governing document elsewhere specifies the exact threshold. The spec carries that exact value. A spec that preserved "roughly equal" would not be reproducible — two agents reading it could implement different thresholds and produce different behaviour.

"Earned through reading" is design intent. Intent belongs in the governing document. The spec translates intent into a mechanism: persona is computed from perspectives read per path, recomputed on every route change, never declared by the user.

**What is excluded:**
The name of the service or function that computes the persona. The spec describes the operation — its inputs (perspectives read per path), its logic (comparison and threshold), and its output (a persona state). The implementation name is excluded. An agent building from this spec chooses the name.

## Content macro — the invariant and the variant

**Governing document says:**
> *"Each perspective has been written [N] times — once for each persona reading it without prior context, and once for each of the seven other perspectives a reader might have arrived from."*
> *"A continuation does not restate what came before. It begins where the previous argument ended."*

**Spec produces:** `narrative-matrix` model, `governing-brief` rule, `continuation-rule` rule.

**Translation decisions:**

The count (N perspectives × M previous states × P personas = total variants) is derived from the authored content. The spec carries the total count and the matrix dimensions as model facts. They are not implementation — they are the authored content structure.

The continuation rule translates almost verbatim. The governing document was already precise: "does not restate," "begins where it ended." Precise governing language becomes spec language with minimal transformation. This is one signal that a governing document is well-written: its constraints translate directly to rules.

**What is excluded:**
The key format used to index the narrative variants in the key-value store. The spec describes what the store contains and what the lookup operation does. It does not describe the key format — that is an implementation choice.

---

## Time macro — precision is not optional

**Governing document says:**
> *"A new session begins when [duration] passes without activity."*
> *"When a session ends, the sequence compresses to its last element… Sessions are capped at [n]. Older sessions are dropped entirely."*
> *"The cookie expires after [duration]."*

**Spec produces:** `session-boundary` rule, `session-decay` rule, `cookie-expiry` rule.

**Translation decisions:**

Every duration and count in this section is an authored decision. The spec carries each one exactly. This is the most important principle for a spec that governs time-based behaviour: vague constraints produce divergent implementations.

A spec that said "a reasonable inactivity period" would allow an agent to use 10 minutes, 30 minutes, or 2 hours — all "reasonable." A spec that carries the authored duration produces the same session boundary every time.

**What is excluded:**
The constant name in code. The spec says "30 minutes" (or whatever the authored value is). The implementation might call this `SESSION_THRESHOLD_MS`, `inactivityLimit`, or anything else. The name is not the spec's concern.

The cookie name is also excluded. The spec describes what the cookie stores and when it expires. The name under which the cookie is stored is an implementation detail — changing it does not change the system's behaviour.

## Trust macro — the bar, the document, and the clear action

**Governing document says:**
> *"The GoverningBar at the bottom of the page shows the site's current read of your session. Three fields, two buttons."*
> *"Clearing requires two clicks."*
> *"The key is never stored."*

**Spec produces:** Three `component` micros for the fields, two mesos for the overlay panels, one `operation` micro for the clear action, one constraint in the AI toggle component.

**Translation decisions:**

"Two clicks, not one" is a governed UX rule. It appears in the spec as an operation constraint. An agent building the clear action must implement the two-click pattern — they cannot substitute a single-click confirmation. The governing document was explicit. The spec carries the explicitness.

"The key is never stored" is a security constraint embedded in the component definition. It is not a separate rule micro — it qualifies the behaviour of the AI-assisted toggle. A constraint that tightly bound to a single component belongs in that component's definition, not as a standalone rule.

**What is excluded:**
The specific text of the confirmation message ("This cannot be undone") is a content decision, not a spec decision. The spec says a confirmation is required before the action executes. The wording is for the content layer.

The component and service names are excluded throughout. The spec describes what the bar displays and what the overlays contain. It does not name the Angular components, the services, or the file paths.

## The exclusion test

For every candidate spec entry, ask:

**Could this spec be built with a different technology stack and produce the same system?**

If yes — the spec is correct.
If a technology name in the spec would force a particular stack — the spec has gone too far.

**Exclude if:**
- It names a framework, library, or language (Angular, React, Firebase, Firestore, TypeScript)
- It names a file or a function (service names, method names, file paths)
- It describes HOW something is implemented rather than WHAT it does
- It is a convention of one implementation that another might not share

**Retain if:**
- It was decided by the author (exact values, named states, prescribed behaviours)
- It is a constraint that governs behaviour across any implementation
- Removing it would allow an agent to make a different decision and produce a different system
- It names what the system does, not how it does it

---

## What this means for reading a spec as an agent

A Catenator spec is read by an agent as a set of constraints to satisfy, not as instructions to follow. The agent asks of each micro: what must be true of my implementation for this to be satisfied?

A `rule` micro must be enforced. A `model` micro must be represented. An `operation` micro must be achievable. A `component` micro must exist with the described responsibilities.

The agent is free to choose implementation details — names, languages, frameworks, file organisation — as long as every spec entry is satisfied. The spec governs the what. The agent chooses the how.

This is why technology details have no place in a spec: they constrain the agent's choices without constraining the system's behaviour. A spec that names Angular has told the agent something about the how that the spec has no authority to specify. Only the governing principle — the author — has that authority.
