# Experience

The experience view examines how the system is perceived and governed for the actor.

The interface view answers what meets. The experience view answers how that meeting is governed — the design decisions that shape what the actor encounters, in what order, under what conditions. Experience is not decoration applied after the system is built. It is a governing condition authored before it. A system without an experience view has made experience decisions implicitly. The experience view makes them explicit.

The experience view is universal. Any system that has an actor has an experience view — a warehouse management system, a clinical tool, a digital publication. The vocabulary differs by domain. The view applies regardless.

---

## What experience covers

| Name          | Description                                                                                                                                                                                                                                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Persona**   | the named behavioural mode the actor occupies at the moment of encounter. Not a demographic profile — a governed description of intent. The designer authors the personas. The system infers which is active.                                                                                                                |
| **Screen**    | the rendering surface and its governing constraints — viewport, device context, grid, and zones. Screen is not a pixel width. It is a capability context. The designer governs screen by defining what a layout must hold, not by specifying breakpoints.                                                                    |
| **Context**   | what the system knows about the actor before they act — entry signals, referrer, session history, ambient conditions. Context establishes the initial governing state before any actor signal fires.                                                                                                                         |
| **Content**   | the governed arrangement of content objects within the active layout state — what is present, what type it is, and what rules govern its authorship, hierarchy, and display. Content is not what the system happens to show. It is what the designer has specified the system must show, to whom, and under what conditions. |
| **Layout**    | the named interface configuration active for the current persona position. The designer authors a finite set of layout states. The system selects the active state from the governing inputs. The layout is not chosen case by case — it is a consequence.                                                                   |
| **Hierarchy** | the ordered arrangement of content and components by prominence within the current layout state. Hierarchy is not a static editorial decision — it is governed by the current persona weights and updated as they shift.                                                                                                     |
| **Time**      | how the system holds and forgets across the actor's session and across return visits. A governed experience remembers the actor's journey. The stateless reset is never neutral — it is a structural message that everything the actor did before does not count here.                                                       |
| **Trust**     | the conditions the actor must satisfy before they act, and the signals the system must provide to meet them. Trust is a governing condition, not a visual treatment. A system that cannot be read, corrected, or understood by the actor it serves has broken trust by design.                                               |

---

## Experience and intent

Intent is the goal state the actor is trying to reach. The experience view is where the system's governing response to that intent is specified — what the system surfaces, in what order, at what prominence, through which layout, under what trust conditions.

Intent cannot be governed without naming the persona it belongs to. The experience view is always specified per persona. A system with three personas has three experience specifications — one for each, composing into a governed whole.

---

## Experience in practice

Examined through the experience view, an `actor` descriptor answers:

- What persona does this actor occupy?
- What behavioral mode governs their intent?
- What layout state is active for this persona?
- What content hierarchy serves this actor in this state?
- What trust conditions must be met before this actor acts?

Examined through the experience view, a `component` descriptor answers:

- What is this component's prominence in the current persona state?
- Which persona weight governs its visibility?
- What anticipatory links does it surface?
- How does it behave across state transitions?

Examined through the experience view, a `rule` descriptor answers:

- What governing conditions shape the actor's perception of this rule?
- What trust signals accompany its enforcement?
- Is the rule legible and correctable by the actor it constrains?

**Experience is not what the system looks like. It is the governed conditions under which the actor encounters it. The designer authors those conditions. The system executes them.**
