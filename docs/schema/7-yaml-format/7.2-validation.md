# Validation

A Catenator spec is valid when it satisfies all structural requirements and all semantic requirements defined in this section. A spec that fails either level MUST NOT be executed by any agent or tool.

Validation operates at two levels: **structural** and **semantic**. Both must pass.

---

## Structural validation

Structural validation checks that the spec is correctly formed — required fields are present, types are correct, and the hierarchy is intact. Structural validation does not require access to the vocabulary or spec library.

### Required fields

A spec fails structural validation if any of the following are absent:

**Spec header:**
- `spec.version`
- `spec.authored`
- `spec.status`
- `spec.standard-version`
- `spec.vocabulary-version`
- `spec.library-version`

**System:**
- `system.name`
- `system.display-name`
- `system.display-name-source`

**Every macro:**
- `name`
- `display-name`
- `display-name-source`
- At least one `meso`

**Every meso:**
- `name`
- `display-name`
- `display-name-source`
- At least one `micro`

**Every micro:**
- `name`
- `display-name`
- `display-name-source`
- `descriptor`
- `definition`

### Type constraints

| Field | Required type |
|---|---|
| `spec.version` | semver string — `MAJOR.MINOR.PATCH` |
| `spec.standard-version` | semver string |
| `spec.vocabulary-version` | semver string |
| `spec.library-version` | semver string |
| `spec.authored` | ISO date string — `YYYY-MM-DD` |
| `spec.status` | one of: `draft`, `ground-truth`, `published`, `deprecated` |
| `system.display-name-source` | one of: `authored`, `inferred` |
| `macro.display-name-source` | one of: `authored`, `inferred` |
| `meso.display-name-source` | one of: `authored`, `inferred` |
| `micro.display-name-source` | one of: `authored`, `inferred` |
| `micro.descriptor` | one of: `model`, `operation`, `rule`, `event`, `process`, `actor`, `service`, `integration`, `utility`, `risk` |
| `macro.injected` | boolean — `true` or `false` if present |

### Hierarchy constraints

- A spec MUST contain exactly one `system` block.
- A spec MUST contain at least one macro.
- Every macro MUST contain at least one meso.
- Every meso MUST contain at least one micro.
- Meso `name` values MUST be namespaced to their parent macro — format: `macro-name.meso-name`.
- `display-name-source` MUST be present on every item that has a `display-name`. A `display-name` without a `display-name-source` is invalid.

### Name constraints

- `system.name` MUST be kebab-case.
- `macro.name` values MUST be unique within the spec.
- `meso.name` values MUST be unique within their parent macro.
- `micro.name` values MUST be unique within their parent meso.
- No name field may be empty.

## Semantic validation

Semantic validation checks that the spec is meaningful — vocabulary references resolve, attachment refs exist in the manifest, and version fields correspond to known releases.

### Vocabulary address resolution

If a micro declares a `vocabulary` field, the address MUST resolve against the `spec.vocabulary-version` pinned in the header. A vocabulary address that does not resolve at the pinned version MUST be flagged as a warning — not a hard failure. The micro definition stands on its own if the address does not resolve.

Format requirement: vocabulary addresses MUST follow the dot-separated path structure defined in section 7.1. Malformed addresses — wrong separator, empty segments — are a hard failure.

### Attachment resolution

If a spec references an attachment via a `ref` field, that path MUST appear in `manifest.yaml` with a valid `sha256` entry. An attachment reference with no matching manifest entry is a hard failure. The file at the referenced path MUST exist in the bundle.

### Version field validation

`spec.standard-version`, `spec.vocabulary-version`, and `spec.library-version` MUST correspond to versions recorded in the version registry (`VERSIONS.md` in the `catenator-standard` repository). A spec pinned to an unrecognised version MUST be flagged as a warning — the spec may have been authored against a pre-release or private version.

### `display-name` consistency

If `display-name-source` is `authored`, the `display-name` value MUST NOT be empty or null. An authored name that is empty is a hard failure — it signals the author intended to specify a name but did not.

If `display-name-source` is `inferred`, an empty `display-name` is permitted — the agent will infer. However, a non-empty suggested value is strongly recommended.

---

## Validation outcomes

| Outcome | Meaning |
|---|---|
| **Valid** | All structural and semantic checks pass. The spec may be executed. |
| **Invalid — hard failure** | One or more required fields are absent, types are incorrect, hierarchy is broken, or authored display-names are empty. The spec MUST NOT be executed. |
| **Valid with warnings** | Structural checks pass. One or more semantic warnings present — unresolved vocabulary address, unrecognised version. The spec MAY be executed with caution. Warnings MUST be surfaced to the author. |

---

## Validation does not cover

Validation checks form and reference — not intent. A spec that is structurally valid and semantically consistent may still be incomplete, incorrect, or insufficiently detailed for a given agent to execute. Validation is a necessary condition for execution, not a sufficient one.

Specifically, validation does not check:

- Whether the selected macros are appropriate for the described system
- Whether the prose in `source` fields accurately justifies the selected items
- Whether the `definition` fields are accurate or precise
- Whether the spec is complete enough to produce a working system

These are matters of spec quality — covered by the -ilities (section 4.2) — not structural validity.
